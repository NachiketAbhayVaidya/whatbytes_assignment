# GigTasks — How It Works

A task manager for gig workers built with **Flutter + Firebase Authentication + Cloud Firestore**.
This document explains every part, what triggers what, and the reasoning behind each decision.

---

## 1. The 30-second summary

- **Flutter** (one Dart codebase) builds the app for Android, iOS and web.
- **Firebase Auth** handles sign up, login, forgot password and change password (email + password).
- **Cloud Firestore** stores each user's tasks in the cloud, in real time.
- The UI **listens to a Firestore stream**. Whenever data changes, the screen rebuilds itself automatically. We never manually refresh the list.
- **Local notifications** remind the user about tasks. They are scheduled on the phone itself, with no server involved.

  theme.dart                     Light/dark themes, custom colors, ThemeController
  models/

  services/

    task_service.dart            All Firestore reads/writes for tasks
    notification_service.dart    Schedules local notifications
  screens/
    auth_screen.dart             Login / Sign up / Google / Forgot password
    profile_gate.dart            After login: Home if the user has a username, else "choose username"
    choose_username_screen.dart  Pick a unique @username (new Google users, older accounts)

    task_form_screen.dart        Create / edit a task

  widgets/
    task_tile.dart               One task card (swipe to delete, checkbox, link)
    stats_strip.dart             Progress bar + weekly stats

**Why this split?** Screens only show UI. Services talk to Firebase. Models hold data and pure logic. That keeps logic testable (the unit tests never need Firebase) and means a backend change would only touch `services/`.

## 4. App start-up (what happens when you open the app)

`main.dart`, in order:

1. `Firebase.initializeApp(...)` connects to our Firebase project using `firebase_options.dart`.
2. `NotificationService.init()` sets up notifications (timezone + plugin). Does nothing on web.
3. `ThemeController.load()` reads the saved light/dark choice from the device.
4. `runApp(...)` starts the UI.

Then a **`StreamBuilder` on `FirebaseAuth.authStateChanges()`** picks the first screen:

- Logged out → `AuthScreen`
- Logged in → `HomeScreen`

This is the key trick: **there is no manual navigation after login or logout.** Firebase announces "the user changed", the stream emits, and the `StreamBuilder` swaps the screen. It also means the user **stays logged in** after closing the app, because Firebase restores the session.

## 5. Authentication

### Unique username (sign up)
- Sign-up has an extra **Username** field: 3-20 letters, numbers or `_`. It is **case-insensitive** (`Sam` and `sam` are the same name).
- While typing, the app checks availability after a 500 ms pause (debounce) and shows a spinner, a green tick (free) or a red cross (taken).
- **How uniqueness is guaranteed:** Firestore document ids are unique, so each name is claimed as a document `usernames/{lowercase-name}` containing the owner's `uid`. The security rules only allow **creating** that document if it doesn't already exist, and never allow update or delete. So two people cannot hold the same name, even if they sign up at the same instant (the database decides, not the app).
- **Sign-up order (`AuthService.register`):**
  1. Check the name is free (a public single-document read).
  2. Create the Firebase account.
  3. In **one atomic batch**, create `usernames/{name}` and the profile `users/{uid}`.
  4. Save the name as the account's `displayName`.
  5. If step 3 fails (someone grabbed the name a millisecond earlier), the new account is **deleted** again and the user sees "That username is already taken", so no account is ever left without a username.
- While steps 2-4 run, the app stays on the sign-up screen (`AuthService.registering` flag), so a failure can show its error there and the user never sees a half-created account.
- **Where it appears:** after login, the home header shows `@username`, and the account menu's first entry shows `@username` plus the email. It is read from the account's `displayName`, so it is instant and needs no extra database read.
- Accounts created before this feature have no username, so they fall back to showing the email.
- Logging in is still with **email + password** (not username). Looking up an email from a username would require exposing emails publicly, which is a privacy risk, so I avoided it.

### Google sign-in
Google is just another Firebase Auth *provider*, so it goes through Firebase like email/password:
1. The user taps **Continue with Google** and picks an account in Google's own popup (`google_sign_in`).
2. Google returns an **ID token**. We hand it to Firebase with `signInWithCredential(GoogleAuthProvider.credential(idToken: ...))`.
3. Firebase creates or finds the user and the normal `userChanges` stream moves the app on. The user has an ordinary Firebase `uid`, so tasks, security rules and reminders work exactly as for email users.
- **Web** uses Firebase's `signInWithPopup` instead (different mechanism, same result).
- **Setup needed:** the Google provider enabled in the Firebase console, plus the app's **SHA-1/SHA-256 signing fingerprints** registered in Firebase (that creates the Android OAuth client inside `google-services.json`). Without a registered fingerprint, Google sign-in fails with an `ApiException 10`-style error; the app catches this and shows "Google sign-in isn't set up for this build. Please use email and password instead." Closing the account picker is not treated as an error.
- **Usernames for Google users:** a Google account has no `@username`, so `ProfileGate` (in `profile_gate.dart`) watches the user's `users/{uid}` profile document:
  - profile exists -> Home screen;
  - profile confirmed missing by the server -> **Choose your username** screen (prefilled from the email, same live availability check and same unique-name claim as sign-up);
  - server unreachable -> after 6 s it lets the user into their tasks instead of blocking them. A "missing" answer that only came from the local cache is *not* trusted, so an offline user is never wrongly asked to pick a username.
  Older accounts created before usernames existed are caught by the same gate.
- **Change password** is hidden for Google-only accounts because they have no password.
- **iOS** is not configured (needs a Mac, a `GoogleService-Info.plist` and a URL scheme).

### Sign up / Log in (`auth_screen.dart`)
- One screen with a toggle between Log in and Sign up (`_isLogin`).
- Tapping the button runs `_submit()`:
  1. The form validators run (valid email format, password ≥ 6 chars).
  2. Calls `signInWithEmailAndPassword` or `createUserWithEmailAndPassword`.
  3. **Success:** `authStateChanges` fires, and the app goes to Home automatically.
  4. **Failure:** `FirebaseAuthException` is caught and `AuthService.message()` converts the code into a readable message.

### Error messages (`AuthService.message`)
| Firebase code | What the user sees |
|---|---|
| `invalid-credential` / `wrong-password` / `user-not-found` | "Incorrect email or password." |
| `email-already-in-use` | "An account already exists for that email." |
| `weak-password` | "Password must be at least 6 characters." |
| `invalid-email` | "That email address looks invalid." |
| `network-request-failed` | "Network error. Check your connection." |
| `too-many-requests` | "Too many attempts. Please try again later." |

Newer Firebase returns `invalid-credential` for both wrong password and unknown email on purpose. This stops attackers from discovering which emails are registered, which is why the message is intentionally the same.

### Forgot password
- The user types their email, then taps **Forgot password?**.
- `sendPasswordResetEmail(email)` makes **Firebase email a reset link**.
- The user sets a new password on a Firebase-hosted page. Our app never sees the new password.

### Change password (`change_password_dialog.dart`)
- Account menu → Change password.
- Needs current password + new password + confirmation (must match, ≥ 6 chars).
- `AuthService.changePassword` does **re-authentication first** (`reauthenticateWithCredential`) and then `updatePassword`.
- **Why re-authenticate?** Changing a password is sensitive. Firebase requires a recent login, so a stolen unlocked phone can't silently change the password. A wrong current password gives the error message.

### Logout
Account menu → Log out. This cancels all scheduled reminders, signs out of Google (so the account picker shows next time) and calls Firebase `signOut()`. The auth stream fires with `null` and the app returns to the login screen.

## 6. Data: where tasks live

### Firestore structure
```
usernames (collection)            <- claims that make usernames unique
  └── {lowercase-name}  { uid, username }

users (collection)
  └── {uid} (document = profile)  { username, usernameLower, createdAt }
        └── tasks (sub-collection)
              └── {taskId} (document = one task)
```
Each user's tasks sit under their own `uid`.

### A task document
| Field | Type | Notes |
|---|---|---|
| `title` | string | required |
| `description` | string | optional |
| `dueDate` | timestamp | includes the time of day only if `hasTime` is true |
| `hasTime` | bool | false = date-only task |
| `priority` | string | `low` / `medium` / `high` |
| `completed` | bool | |
| `completedAt` | timestamp or null | set when marked complete; powers "done this week" |
| `pay` | number or null | optional earnings (my extra) |
| `remindMinutes` | number | minutes before due time; `-1` = no reminder |
| `link` | string or null | optional web link |

`Task.toMap()` converts a Task into this map. `Task.fromDoc()` converts back. Old documents missing newer fields still work because `fromDoc` uses defaults (for example `remindMinutes` defaults to 0).

### Security rules (`firestore.rules`)
```
match /users/{uid}/tasks/{taskId} {
  allow read, write: if request.auth != null && request.auth.uid == uid;
}
```
Meaning: **you can only read or write tasks under your own uid, and only when logged in.** One user can never see another user's tasks, even with the app's API keys. Everything else is denied by default.

Rules for usernames:
- `usernames/{name}`: anyone may `get` one name (so availability can be checked before the account exists) but **nobody can list them**. A logged-in user may **create** a name only if it matches `[a-z0-9_]{3,20}`, is stored in lowercase as the id, and the `uid` field is their own. **Update and delete are always denied**, so a name can't be stolen or changed.
- `users/{uid}` (profile): readable only by its owner, create-only, and the create is rejected unless the matching username claim is written in the same batch (`getAfter(...)`).
- I tested these rules against the live project with two throwaway accounts: claiming a free name works; the same name in a different case is rejected; claiming a name on behalf of another uid is rejected; overwriting someone's name is rejected; anonymous users can't list or write; users can't read each other's profiles or tasks. The test data was deleted afterwards.

**Are the API keys in `firebase_options.dart` a secret?** No. Firebase client keys only identify the project. Security comes from the rules above.

## 7. The home screen: what triggers what

### The live list
`HomeScreen` creates `TaskService(uid).watch()`, which is
`collection.orderBy('dueDate').snapshots()`.
A `StreamBuilder` listens to it. **Any change to the database (add / edit / delete / complete) makes Firestore push a new list, and the screen rebuilds.** That is why after saving a task the list updates by itself without any refresh code.

### Trigger table

| User action | What runs | Result |
|---|---|---|
| Tap **+** | opens `TaskFormScreen` | blank form |
| Tap **Create task** | `TaskService.add()` | Firestore doc created → stream emits → list updates → reminders re-sync |
| Tap a task | opens form with that task | edit mode |
| Tap **Save changes** | `TaskService.update()` | same chain as above |
| Tick the checkbox | `setCompleted(id, bool)` | sets `completed` and `completedAt` → list, stats and reminders update |
| Tap the trash icon on a card, swipe it left, or tap the red trash in the edit screen | `TaskService.delete()` | doc removed, snackbar with **Undo** (all three paths) |
| Tap **Undo** | `TaskService.restore()` | re-creates the doc with the same id |
| Type in search | `setState(_query)` | list re-filtered instantly (no network) |
| Tap a filter chip | `setState` | list re-filtered instantly |
| Tap link on a card | `openLink()` | opens browser |
| Avatar → Dark mode | `ThemeController.set()` | whole app recolors and the choice is saved |

### Sorting, filtering, searching (`_apply`)
All done **on the phone** after the data arrives:
1. Filter by priority (if a chip is selected).
2. Filter by status: All / Incomplete / Completed.
3. Filter by search text (title or description, case-insensitive).
4. Sort by `dueDate` ascending (earliest first).

**Why client-side and not Firestore queries?** Combining `where` filters with `orderBy` on different fields requires creating composite indexes in Firestore. A personal task list is small, so filtering locally is instant, works offline, and avoids index setup.

### Grouped sections (`task_grouping.dart`)
After sorting, `groupTasks` puts each task into a section:

| Section | Rule |
|---|---|
| **Overdue** (red) | not completed and the due date/time has passed |
| **Today** | due today |
| **Tomorrow** | due tomorrow |
| **This week** | due in 2–7 days |
| **Later** | due after that |
| **Earlier** | completed tasks from the past |

The list is flattened into headers + tasks and shown in one scrolling list (`SliverList`). Dates are compared as UTC calendar days so daylight-saving changes can't shift a task into the wrong section.

### Stats strip (`computeStats`)
- **Progress bar:** completed ÷ total.
- **Done this week:** completed tasks whose `completedAt` is on/after this Monday.
- **Overdue:** incomplete tasks past due.
- **Earned this week:** sum of `pay` over the "done this week" tasks.
- Weeks start on Monday.

## 8. Notifications (the part they will probably ask about)

### What it is
**Local notifications.** The phone itself schedules and shows them. No server, no Firebase Cloud Messaging.

### When is a reminder scheduled?
Each task has `reminderAt` (computed in `task.dart`):

- **Task with a time:** `dueDate − remindMinutes` (for example due 6:00 PM, remind 1 hour before → 5:00 PM).
- **Date-only task:** **9:00 AM on the due date** minus the offset. The assignment only asked for a due *date*, so we need a default time. 9 AM is the fixed default.
- **"No reminder"** (`-1`) → none.

### The full chain (what triggers what)

```
You add / edit / complete / delete a task
        ↓
Firestore changes
        ↓
watch() stream emits the new task list
        ↓
HomeScreen's listener calls NotificationService.sync(tasks)
        ↓
plannedReminders():  drop completed tasks, tasks with no reminder,
                     and reminders already in the past;
                     sort soonest first; keep only the 60 soonest
        ↓
cancelAll()  then  zonedSchedule() for each planned reminder
        ↓
Android/iOS alarm manager fires the notification at that time
```

### Why "cancel everything and reschedule" every time?
It is the simplest way to guarantee the notifications always match the database. Deleted tasks lose their reminder, edited tasks get the new time, completed tasks stop reminding, and a fresh login on another phone rebuilds them. There is no extra bookkeeping to go wrong.

### Details worth knowing
- **Permission:** Android 13+ and iOS need the user to allow notifications. The app asks when the home screen opens (`requestPermission`). If denied, nothing is shown.
- **Queue:** `sync` calls run one after another. Firestore emits twice at start-up (cache, then server). Without the queue, an older list could finish scheduling *after* a newer one and leave a reminder for a deleted task.
- **60 limit:** iOS only keeps 64 pending notifications, so we schedule the 60 soonest.
- **IDs:** a simple counter (safe because we cancel all first).
- **After a phone reboot:** the plugin's boot receiver (declared in `AndroidManifest.xml`) restores scheduled alarms.
- **Exact alarms:** reminders use `exactAllowWhileIdle`, so they fire at the chosen minute. I originally used inexact alarms and measured on a real phone that a reminder due at 11:06:00 PM arrived at 11:07:08 PM (Android delivers inexact alarms anywhere in a ~1 minute window, more under Doze). With exact alarms the same kind of reminder arrived 31 ms after the due time. The app declares `USE_EXACT_ALARM` (Android 13+, auto-granted) and `SCHEDULE_EXACT_ALARM` (Android 12), and falls back to inexact alarms if Android ever refuses (`canScheduleExactNotifications`).
- **Timezone:** `flutter_timezone` reads the phone's timezone so 9 AM means 9 AM local time.
- **Logout:** cancels all reminders so the next person on the phone isn't notified about your tasks.
- **Web:** local notifications are not supported, so every call is a no-op there (guarded by `kIsWeb`).
- **Not done:** tapping a notification just opens the app (doesn't jump to the task). Push notifications through FCM were deliberately skipped (they need a server, and iOS push needs an Apple developer account).

## 9. The task form (`task_form_screen.dart`)

- **Title** is the only required field.
- **Due date** uses the date picker; **Time** is optional and clearable (✕).
- **Reminder dropdown changes with the time field:**
  - With a time: No reminder / At due time / 15 min / 1 hour / 1 day before.
  - Without a time: No reminder / 9:00 AM on the day / 9:00 AM the day before.
  - If you remove the time while an option that no longer exists is selected, it resets to a valid one (`_fixReminder`).
- **Pay** accepts only numbers (up to 2 decimals) through an input filter.
- **Link** is validated by `parseLink`: it adds `https://` if missing and rejects spaces and non-web schemes (`javascript:`, `ftp:`). Rejecting `javascript:` links matters for safety.
- **Priority** is a colored segmented button (green / amber / red).
- Same screen for create and edit: if a `task` is passed in, fields are pre-filled and Save calls `update` instead of `add`.

## 10. Theme and dark mode

- `theme.dart` builds a light and a dark `ThemeData` from one purple seed color (`#6C63FF`) using Material 3.
- Extra colors that Material doesn't cover (background, card, muted text, borders) live in a custom `AppColors` **ThemeExtension**, and widgets read them with `context.c`. That way no widget hard-codes a color, and dark mode works everywhere.
- Default follows the phone's setting. The avatar menu toggle switches it and saves the choice with `shared_preferences`. It is restored on the next launch.
- Font is Poppins via `google_fonts`, matching the reference design.

## 13. Likely questions and answers

**Why Firestore and not SQLite / Realtime Database?**
It lives in the same Firebase project as Auth, gives real-time streams, works offline with a local cache on mobile, and security rules tie data to the logged-in user. The assignment allowed "Firebase or any backend".

**Why a stream instead of fetching once?**
Streams keep the UI in sync automatically (even across two devices) and remove the need for refresh code.

**How is one user's data kept from another?**
Data lives under `users/{uid}/...` and the security rules only allow access when `request.auth.uid == uid`.

**What state management did you use?**
Plain Flutter: `StatefulWidget` + `StreamBuilder` + `ValueNotifier` (for theme). The app is small, so adding Provider/Bloc would be extra complexity.

**Why is filtering done on the client?**
The list per user is small, and it avoids Firestore composite indexes and extra reads.

**What happens when offline?**
On Android/iOS, Firestore caches data and queues writes, syncing when back online. Login itself needs a connection. (Web has persistence off by default.)

**What happens if two reminders are for the same time?**
Both are scheduled with different IDs and both show.

**Can a user see someone else's tasks?**
No, the security rules reject it (see section 6).

**What would you improve with more time?**
Tap-to-open from notifications, FCM push notifications, Google sign-in, multiple links per task, categories/tags, recurring tasks, a Firebase emulator test suite, and an iOS build/test on a Mac.

**How do you make usernames unique?**
Each name is a Firestore document id under `usernames/`, and the security rules only allow creating a document that doesn't exist yet. The claim and the profile are written in one atomic batch, so there's no race condition, and the rules (not just the app) enforce it.

**Why not log in with the username?**
It would need a public username-to-email lookup, which leaks users' emails. Email + password is the spec, and the username is used for display.

**What happens if two people pick the same name at once?**
The first batch wins. The second batch is rejected by the rules, the second account is deleted, and that user sees "That username is already taken".

**How does Google sign-in work, and why might it fail for someone else?**
It's a Firebase Auth provider: Google gives us an ID token and Firebase turns it into a user. On Android it only works for builds whose signing-key fingerprint is registered in Firebase. My debug key is registered; another machine's debug key isn't, so Google login can fail there (the app shows a friendly message and email/password still works). Registering the other key, or a release key, fixes it.

**Why were notifications late at first?**
They were scheduled as inexact alarms, which Android may deliver anywhere inside a window (I measured 68 s late on a real phone). Switching to exact alarms brought it to 31 ms.

**Which parts are beyond the assignment?**
Google sign-in, unique usernames, forgot/change password, reminders, time, search, sections, stats, pay, link, undo, dark mode. All are optional; the core spec works without them.
